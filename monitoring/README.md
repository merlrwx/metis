# Metis operations

Import `grafana-dashboard.json` and choose the Prometheus data source. `prometheus.yaml` is a Compose-network scrape example; load `metis-alerts.yaml` into your existing Prometheus. Kubernetes API and worker pods advertise scrape annotations; configure the existing collector's pod discovery to honor them. Each worker runs one Taskiq process and exposes metrics on port 9100. Scrape each pod, rather than a load-balanced Service, to count every worker. Do not sum the database-wide queue/connection gauges from API replicas: use `max`, as the dashboard does.

The API exposes `/metrics` on port 8000. Keep metrics on an internal network; they contain aggregate operational information. Labels use route templates and status codes, never tenant IDs, document text, query strings, emails or prompts. The `metis` logger writes JSON events with request IDs and worker lifecycle job/organisation IDs, without exception messages that might contain document content. `X-Request-ID` accepts up to 64 ASCII letters, digits, dashes or underscores; other values are replaced. Database timing does not log SQL or parameters.

Worker counters and histograms reset on restart; use Prometheus rates. Queue depth and oldest age derive from durable pending/queued database jobs. Active workers use Redis heartbeat keys with a 30-second TTL. Heartbeats disappearing trigger an alert after two minutes. Requests returning errors, model calls, retrieval, RAG, database queries and ingestion attempts have separate latency/error measurements. An embedding request counts one provider call, which may use several batches internally.

The `reconcile-jobs` CronJob runs every two minutes, republishes at most 100 pending jobs older than two minutes and locks their rows while publishing. Already queued, processing, indexed and failed jobs are excluded. No tenant content enters Redis; each message carries the original organisation/job IDs. Publication failure rolls back database changes and fails the CronJob, preserving pending work for the next run. Run `metis-reconcile` manually in the same configured environment if required. Monitor failed CronJobs in your existing Kubernetes job alerts.

For an ingestion alert, inspect `job_attempt_failed` events, the job's status and error through an authorized tenant API, and storage/embedding availability. Restore the dependency, then retry a failed document through the UI. For worker alerts, check pod logs and Redis connectivity. For waiting-age alerts, check both worker availability and the reconciliation CronJob. Slow-query events contain duration only; use PostgreSQL monitoring under your platform's access controls for SQL investigation. No autoscaler is introduced until measured load justifies one.
